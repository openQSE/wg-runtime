## Purpose

The meeting focused on whether the working group should define, or at least describe, a shared runtime/task interface across quantum and classical/HPC systems. The discussion centered on how far down the stack such a runtime should go: application-level orchestration, device-side runtime mechanisms, or interfaces close to QPU control hardware.

## Executive Summary

The group explored whether lessons from CUDA/ROCm-style runtimes can inform quantum-classical runtime design. The presenter used GPU runtimes as a concrete model, especially streams, task graphs, graph capture, synchronization, logical work items, scratchpad memory, and launch APIs. These examples highlighted how a runtime can separate logical work descriptions from physical hardware scheduling while still exposing enough control for performance-sensitive applications.

Participants pushed on where that analogy breaks down for quantum systems. In the current quantum ecosystem, vendors often own the closed runtime/control stack, including compilation and hardware-specific lowering. This limits opportunities to insert a shared device-side runtime below the vendor API. The group distinguished at least two interface levels: an application-facing interface that orchestrates work across QPUs, CPUs, GPUs, FPGAs, and other devices; and a lower-level runtime/control interface closer to QPU execution, error correction, topology, and timing constraints.

By the end, participants converged on the need to avoid getting lost in low-level detail before defining scope. A proposed next step is to create a document that sketches requirements for both interface levels, identifies user personas, and compares where other working groups already define hardware/resource representations.

## Key Takeaways

- There is no clearly shared device-runtime/task interface across quantum and HPC stacks today.
- CUDA/ROCm provide useful examples of runtime design, especially streams, task graphs, graph capture, launch configuration, memory hierarchy, and synchronization.
- The GPU analogy is helpful but incomplete. Classical runtimes often let users launch more logical work than physical hardware can run at once; QPU execution may not allow the same oversubscription model.
- Quantum systems have stricter and more layered timing constraints, especially around pulses, physical control, and error correction.
- Vendors currently hide much of the QPU runtime/control stack. A shared interface may only be realistic at a higher abstraction layer unless vendors expose lower-level contracts.
- The group sees value in separating at least two discussions:
  - Application-facing orchestration across heterogeneous resources.
  - Lower-level device/runtime interfaces near QPU control, topology, and latency-sensitive operations.
- The application-facing interface appears more immediately feasible and better aligned with several participants' priorities.
- The low-level runtime interface remains worth considering, but it may overlap with vendor internals and other working groups.

## Discussion Notes

### 1. Motivation: Missing Shared Runtime Interface

The presenter opened by noting that quantum and HPC stacks lack a standard runtime/task interface shared across systems. The suggested scope was not only scheduler-level runtime, such as Slurm or job dispatch, but runtime closer to devices.

The initial framing emphasized heterogeneous systems: GPUs, CPUs, FPGAs, AI engines, QPUs, and other accelerators. The presenter argued that GPUs are a useful comparison point because heterogeneous quantum systems will likely include classical accelerators and because GPU runtimes have already developed mechanisms for latency, concurrency, task launch, memory movement, and synchronization.

### 2. GPU Runtime Concepts Used as Analogy

The presenter walked through CUDA/ROCm runtime concepts:

- Device contexts expose hardware properties such as compute units, scratchpad/shared memory, and HBM capacity.
- Applications split work between host code, usually CPU-side, and device kernels or shader code.
- The CUDA triple-chevron launch API expresses kernel launch configuration.
- Grid and block dimensions represent logical work items that are scheduled onto physical GPU resources.
- Shared memory, scratchpad memory, or LDS gives software-controlled memory close to compute units.
- Streams express concurrency and sequential ordering.
- Events synchronize work across streams.
- Device and stream synchronization define when host-side code must wait.
- Grid-level synchronization can happen within a GPU kernel without returning to the host.
- Graph capture and explicit graph construction reduce launch latency by batching task graphs rather than issuing many individual kernel launches.

The presenter highlighted launch latency as an important analogy for quantum workloads. If many small operations each require a separate launch, overhead can dominate the actual compute or device work. GPU graph capture was presented as one solution to this problem in classical accelerators.

### 3. Scope Question: Torch-Like Layer or Below Torch?

A participant asked whether the group is trying to build something like Torch at the application level or something below Torch that provides lower-level device access. They noted overlap with existing efforts that unify device descriptions and capabilities.

The presenter clarified that their own work, specifically Space RT, is closer to device-side runtime. The target is the layer used to build operations that higher-level APIs later call, rather than the high-level application framework itself. Space RT was described as targeting GPUs, NPUs, AI engines, FPGAs, and quantum computers, though the presenter qualified that this does not mean every device is equally supported today.

The discussion then turned to whether hardware vendors, especially quantum vendors, expose enough low-level access for such a runtime. Participants observed that QPU vendors typically control their hardware stack and may not expose the level of access needed to install or target a low-level runtime.

### 4. Abstraction Layers in Quantum Systems

Participants repeatedly distinguished between levels of abstraction:

- Physical control level: pulses, timing, and direct hardware control.
- Error-correction/control level: surface codes or other error-correcting code implementation, likely with stringent real-time latency requirements and possibly FPGA/control-system involvement.
- Logical qubit/application level: applications interact with logical qubits or vendor-provided operations without needing details of physical qubits or pulses.
- Heterogeneous orchestration level: application code coordinates QPU, CPU, GPU, FPGA, and other resources.

One participant emphasized that an application developer using error-corrected logical qubits generally should not need to know how error correction is implemented. In current hardware, physical qubits are closer to the real user-visible device, but in an error-corrected era the logical/physical split will become more important.

The group agreed that different layers have different latency requirements. Physical control and error correction may require extremely tight timing, while higher-level application orchestration can tolerate looser timing, though latency still matters.

### 5. Compiler Versus Runtime Boundary

The group discussed where compiler responsibilities end and runtime responsibilities begin.

The presenter described the compiler as responsible for mapping logical code to something executable on the device, while the runtime is responsible for taking the compiled artifact and launching or scheduling it on the target system. In GPU terms, the compiler understands details such as work items, memory allocation, and generated device code, while the runtime handles launch configuration, stream placement, and orchestration.

Participants noted that in quantum systems this separation is less clear. Vendors may perform additional compilation after submission, lowering circuits to hardware-specific instructions inside closed systems. This makes it hard to inject an external runtime between "compile" and "run."

A possible path was discussed where a high-level representation, possibly HUGR-like, could be compiled to an LLVM-like representation that calls into Space RT or a similar runtime. This would require a compiler that lowers the high-level quantum/classical representation into runtime calls and device-specific artifacts.

### 6. Vendor Runtime and Closed-Stack Concern

The group repeatedly returned to the issue that quantum vendors own much of the runtime/control stack. This includes calibration, pulse implementation, hardware-specific gate compilation, timing constraints, and hidden scheduling or lowering phases.

The presenter suggested that even if the quantum part remains vendor-owned, a contract is still needed between the closed QPU stack and the rest of the heterogeneous system. For larger systems with QPUs plus classical accelerators, the open question is what that contract should expose.

One proposed realistic fallback is that the QPU stack handles its own internal runtime while a higher-level heterogeneous runtime submits work to it and coordinates surrounding classical resources. The presenter described this as useful, but different from a true device-side runtime.

### 7. QPU as Specialized Accelerator

The presenter compared QPUs to specialized accelerators inside a larger heterogeneous workload, using GPU tensor/matrix cores as an analogy. In that analogy:

- The programmer does not need to know all details of the matrix core internals.
- The programmer must know how to provide inputs and consume outputs.
- The rest of the kernel or application composes that specialized operation with general-purpose computation.

Applied to QPUs, the idea is that quantum operations might be treated as specialized accelerator calls within a larger application. The exact pulse/control details remain hidden, but the surrounding runtime still needs to know how to schedule work, move data, and coordinate dependencies.

Participants noted that this analogy is useful but limited because QPU capabilities, topology, and timing constraints differ significantly from GPU tensor cores.

### 8. Topology and Device Capability Representation

The presenter asked for examples of QPU topology and the APIs that expose it. Participants discussed that topology may be dynamic or vendor-specific, and that some systems may expose physical qubits today rather than logical ones.

The group noted that other working groups may already be defining hardware/resource representations. The runtime discussion should therefore not duplicate or contradict work from resource management or quantum device interface groups.

The presenter compared this to GPU runtimes, where lower layers such as drivers expose device resources and topology. The runtime consumes this information to decide how to schedule or launch work.

### 9. Classical Versus Quantum Logical Work

The group explored an important difference between GPUs and QPUs. In classical GPU programming, an application can launch more logical work items than there are physical compute units. The hardware scheduler executes them in waves or iterations until all logical work completes.

For QPUs, this may not translate. A quantum application generally cannot express a fully coupled problem larger than the available qubits in the same way. There may be cases where independent quantum subproblems can run separately, for example if a Hamiltonian is block diagonal, but that is different from oversubscribing one coupled circuit across smaller hardware.

The presenter acknowledged this as a classical/quantum difference and noted that a quantum runtime should not blindly copy NVIDIA's design choices.

### 10. Need for Better Scoping and Timeboxing

Near the end, participants noted that the discussion was drifting into detailed technical weeds. A participant suggested timeboxing future meetings more carefully and identifying concrete takeaways.

The group seemed to agree that both application-level and lower-level runtime questions are useful, but that they are distinct use cases and should be handled separately.

## Decisions and Agreements

- The group should distinguish application-facing runtime/orchestration from low-level device-side runtime.
- A shared lower-level runtime for QPUs may be constrained by vendor-controlled stacks and closed compilation/control layers.
- The application-facing interface is more immediately understandable and likely more feasible for the group to define.
- Lower-level runtime requirements should not be ignored, but need clearer examples and boundaries.
- The group should coordinate with other working groups that are defining resource management, hardware capability descriptions, or device access schemes.
- Future discussion should be grounded in concrete examples rather than abstract runtime terminology.

## Open Questions

- Is a device-side runtime for QPUs realistic without vendor participation?
- Which abstraction layer should this working group prioritize: application orchestration, device-side runtime, or both?
- What information should a quantum hardware/resource description expose to a runtime?
- How should topology, dynamic calibration state, and hardware capability changes be represented?
- Can HUGR/LLVM-like lowering provide a useful path from high-level quantum/classical programs to a shared runtime?
- Where should compiler responsibility end and runtime responsibility begin for quantum systems?
- How should timing constraints be represented at application level versus control/error-correction level?
- Are there useful analogs to GPU streams, events, and graph capture for quantum-classical workflows?
- What parts of CUDA/ROCm runtime design are genuinely transferable, and what parts are artifacts of classical accelerator scheduling?

## Risks and Concerns

- Vendor stacks may not expose enough low-level control for an external runtime.
- The group may duplicate or conflict with work from other working groups if scope is not coordinated.
- GPU analogies can clarify concepts but may also mislead if copied too literally.
- Low-level runtime discussions can quickly become too detailed without concrete examples.
- Requirements differ significantly between physical control, error correction, logical qubits, and application orchestration.
