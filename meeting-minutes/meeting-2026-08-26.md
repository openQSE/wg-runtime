## Executive Summary

The group launched the Runtime Working Group to define a runtime layer that presents heterogeneous compute resources to quantum-HPC applications through useful, interoperable abstractions. The discussion built on the July openQSE Day runtime session, including Luke Bertels' application perspective and AMD's initial SpaceRT presentation. Participants viewed the workflow-management system presented by Philip at openQSE Day and task frameworks such as BSC's COMPSs as complementary technologies that should be compared with SpaceRT and SDK runtimes rather than treated as direct substitutes.

The proposed work program has four parts:

1. Gather application requirements to guide the runtime object model and exposed features.
2. Compare existing runtime and workflow approaches, including SpaceRT, Qiskit, TKET, COMPSs, the workflow system presented at openQSE Day, and relevant vendor runtimes.
3. Deploy selected prototypes on the ORNL test bed to evaluate the concepts with working software.
4. Document the findings and recommendations in a paper.

### Application and SDK boundary

Participants distinguished among end-user applications, SDK or framework implementations, and the kernels dispatched to individual compute resources. Application scientists generally expect to use high-level SDK interfaces without managing device placement or resource-specific details. The group therefore wants runtime integration to remain transparent for existing applications where practical, while allowing SDK and framework developers to access heterogeneous capabilities when needed.

The current membership does not fully represent the SDK/framework layer that decomposes an application into kernels and coordinates CPU, GPU, and QPU work. The group agreed to recruit contributors with Qiskit and TKET runtime expertise and to invite additional application developers to present their requirements.

### Runtime abstraction and comparison

A central requirement is support for multiple QPUs and heterogeneous resources through a coherent interface. Existing SDK backends are commonly associated with one device or execution context, leaving applications to manage several backends and coordinate cross-device work themselves. SpaceRT is intended to discover resources visible within an allocation, expose their capabilities and locality, and dispatch kernels through common interfaces.

The comparison work should explain what a unified runtime contributes beyond Qiskit, TKET, CUDA-Q, vendor-specific stacks, and workflow systems. Topics include task dependencies, scheduling, synchronization, resource discovery, device topology, data locality, multi-QPU execution, and the boundary between logical and physical device information. The group did not resolve how much physical detail should be exposed and will continue evaluating the tradeoffs.

### QFw integration

Amir reviewed QFw's current architecture. Quantum Platform Manager Daemons expose device operations and enforce concerns such as authentication and reservation validity. A directory service allows applications to discover registered quantum services, and a Qiskit backend connects applications to those services.

The group discussed placing the runtime beneath the SDK backend to preserve existing application interfaces. New optional APIs could expose heterogeneous device discovery and multi-resource execution without changing existing circuit or error-model descriptions. The precise boundary among the SDK backend, QFw, SpaceRT, compilers, and resource-management interfaces remains an open design question.

### Application workflows and QEC workflows

Participants identified two distinct use cases for heterogeneous execution:

- Application-level hybrid workflows coordinate CPU, GPU, FPGA, and QPU kernels without the strict latency requirements of quantum error correction.
- QEC and near-device workflows coordinate classical accelerators and QPUs under tight latency, locality, security, and hardware constraints.

These use cases should be treated as separate work streams initially so the group can make concrete progress. Participants nevertheless agreed that a sufficiently low-latency runtime such as SpaceRT could provide a common foundation for both. Future fault-tolerant systems may also require some QEC choices to become visible at the application level.
