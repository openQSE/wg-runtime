## Meeting Purpose

The group discussed how to scope the openQSE Runtime Working Group across workflow management, application/runtime orchestration, resource management, and lower-level device runtimes. The meeting converged on using a concrete top-to-bottom prototype to clarify interfaces before attempting a formal runtime specification.

## Discussion Summary

### Runtime Layers and Scope

The group discussed three broad layers:

1. A workflow manager that can describe a high-level application flow and reserve or launch classical and quantum work through systems such as Slurm.
2. An application/resource orchestration runtime for hybrid quantum-classical applications, including co-location and management of classical nodes, QPU access, simulators, and optimization loops.
3. A lower-level device runtime operating after compilation, closer to hardware execution, scheduling, launch, and task-queue management.

There was broad agreement that the working group should begin from the application and workflow level, then work downward. AMD's lower-level SpaceRT/device-runtime work can continue in parallel, with the expectation that the two directions eventually meet in the middle.

Application runtime and co-location runtime were discussed as likely being the same conceptual layer rather than two separate layers.

### SpaceRT and Device Runtime

Xulong described SpaceRT as operating after compilation on a graph or task representation produced by the compiler. In the GPU analogy, SpaceRT is not responsible for compiler transformations such as kernel fusion, but for launching kernels, preparing parameters, managing task queues, scheduling work on hardware, and tuning runtime knobs around latency and throughput.

The group noted that QEC can be an important use case for low-latency runtime behavior, but should not define the first runtime architecture effort. Current hardware makes full error-corrected workflows hard to use as the primary near-term driver.

The group requested a more concrete runnable example showing how SpaceRT interacts with a QPU or quantum workload, so that the boundary between compilation, application runtime, and device runtime can be made clearer.

### Runtime Implementation vs Specification

A question was raised about whether the working group should produce a runtime implementation, a runtime specification, or both. The emerging view was that it is too early to write a useful specification in the abstract. The group should first build a top-to-bottom working prototype, inspect where common interfaces appear, and then use those surfaces to inform specification work.

### Compiler Boundary

The group discussed the difficulty of drawing a hard boundary at compilation. Today many applications can separate classical and quantum code before execution, but this separation becomes less clear if future programs generate quantum code at runtime or invoke quantum compilation dynamically. The group should be careful not to overfit the architecture to today's simple compile-time/runtime boundary.

### Candidate Application: Chemistry Workflow

Luke summarized the chemistry application as a promising first use case:

1. A supermolecular complex is processed by classical code.
2. The classical stage decomposes the problem into smaller monomer and dimer components.
3. A circuit-construction stage builds VQE ansatz circuits or quantum sampling circuits for the decomposed components.
4. A quantum orchestrator schedules and executes the quantum work.
5. Results are reconstructed into energies and properties for the original molecular problem.

Potential feedback loops were discussed:

1. A VQE-level hybrid loop, where circuit results feed into classical parameter optimization.
2. A larger self-consistent loop, where quantum results could update the electrostatic potential or embedding and feed back into the classical chemistry stage.

Luke noted that in prior proof-of-concept runs, the classical portion took on the order of seconds, while the quantum portion took much longer: days on Quantum Brilliance hardware, and potentially hours on faster hardware. A full-size run on IQM has not yet been completed.

The group noted that the decomposed monomer and dimer systems are naturally parallelizable. Prior parallel runs were done with Quantum Brilliance, but not yet on IQM.

### Parallelism and Benchmarking

The group identified several execution patterns worth comparing:

1. Express parallelism at the workflow level, where the workflow graph launches multiple jobs or branches.
2. Submit one Slurm job that reserves multiple resources and performs parallelism internally.
3. Compare workflow-tool execution with a regular Python script or baseline implementation.
4. Compare execution across physical QPU access, emulated/fake QPU services, and simulators.

There was interest in creating a reproducible repository or benchmark harness where different ways of running the same experiment can be compared. The group discussed using timing and scalability measurements to understand where overhead and parallelism appear.

### Testbed and Slurm Environment

Amir described a Docker-based virtual Slurm environment that can act as an intermediate test environment before deployment on the Oak Ridge testbed. The environment is intended to resemble the real testbed closely enough to support collaborative development.

The described virtual environment includes:

1. A normal partition with eight classical nodes.
2. A services partition with a fake IQM backend for interface testing.
3. An IQM backend node that can talk directly to IQM using the IQM client when configured with API keys.
4. A shim path where access to IQM is mediated through QRMI/QDMI.
5. An NWQ-Sim simulator setup with a head node and worker nodes.

The planned real testbed was described as likely including approximately four CPU nodes, one AMD GPU node with eight GPUs, services connected to the IQM rack, and simulator services. The group agreed that developing against the virtual Slurm environment should make it easier to mirror the setup onto the real testbed once available.

### QPU Sharing and Scheduling

Srikar raised the question of whether the runtime should understand the whole stack rather than only Slurm-level parallelism, especially where QPU sharing is a bottleneck. The group discussed time-sharing, space-sharing, interleaved shots, circuit knitting, and resource-aware admission control.

Amir described existing admission-control work where jobs provide metadata such as maximum number of circuits, maximum qubit count, and maximum circuit depth. That metadata can feed resource estimation and allow multiple jobs to be admitted if sufficient QPU capacity is available.

The group agreed that QPU sharing will matter eventually, but should not be the first priority. The immediate goal is to get a baseline prototype running; QPU sharing and scheduling policies can be investigated after that baseline exists.

### Future Use Cases

Luke mentioned a neural-network quantum-state approach where quantum hardware performs Markov chain sampling at the single-shot level. Because this may require lower-latency quantum-classical feedback, it could become a useful future use case. The group discussed possibly involving Manas, who may have code associated with that work.

## Decisions

1. Use the chemistry application as the first concrete top-to-bottom use case.
2. Prioritize a short-term working prototype over an abstract runtime specification.
3. Use the Docker/virtual Slurm environment as the near-term collaboration and integration target.
4. Compare multiple parallel execution approaches, including workflow-level parallelism and internal application/job-level parallelism.
5. Continue SpaceRT and lower-level runtime exploration in parallel, but do not make QEC or device-runtime details the first integration target.
6. Treat QPU sharing and detailed scheduler/admission policies as a later phase after the first end-to-end run is working.

## Open Questions

1. What exact interfaces should separate workflow management, application/resource orchestration, compilation, and device runtime?
2. Where should parallelism be expressed for hybrid applications: workflow graph, Slurm job submission, application internals, or multiple layers?
3. Which surfaces should eventually become runtime specification material?
4. How should the workflow tool interact with QPM/QFW services while QRMI/QDMI remains hidden behind those services?
5. How much QPU sharing information should be exposed at the runtime interface level versus handled by implementation-specific schedulers?
6. What benchmark framework or repository structure should be used to compare execution approaches?

## Plan of Record

The agreed plan is to pursue a concrete top-down prototype before attempting to standardize the runtime interfaces.

1. Start with Luke's chemistry application as the first target use case.
2. Make the application repository available to the working group and have Luke walk through the code at the next meeting, expected in roughly two weeks because of QCE the following week.
3. Deploy and run the application in the Docker-based virtual Slurm environment that mirrors the planned Oak Ridge testbed.
4. Use the prototype to exercise a full hybrid workflow: classical chemistry preprocessing, quantum circuit construction/execution, result reconstruction, and eventual feedback loops where practical.
5. Implement and compare at least two parallel execution models: workflow-level parallel branches/jobs and a single Slurm job that reserves multiple resources and parallelizes internally.
6. Run against available backends and services, including fake/emulated IQM, direct IQM access where available, QRMI/QDMI-backed service paths, and NWQ-Sim simulation.
7. Keep SpaceRT/device-runtime work progressing in parallel and connect it to the top-down prototype once the relevant interfaces and runnable examples are clearer.
8. Use lessons from the prototype to identify common interface boundaries and decide what should become a runtime specification.
9. Defer QPU sharing as a first-class design target until the baseline end-to-end workflow is running, then revisit admission control, scheduling, time-sharing, space-sharing, and stack-wide resource metadata.
